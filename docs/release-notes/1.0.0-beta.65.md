A maintenance release, and two defects that were each invisible for a reason
worth writing down.

## The lockfile said which version it was not

`v1.0.0-beta.64` shipped with `package.json` at beta.64 and
`package-lock.json` still saying beta.63, in both places npm writes it. The
version bump edited one file and nothing regenerated the other, so the
lockfile's bytes were literally the beta.63 file: the same digest on both tags.

Every release from beta.60 to beta.63 agreed, so this was a regression rather
than a habit, and nothing looked for it. `release:check` walks tracked files
for things that must not ship, and the release-notes gate reads `package.json`
alone.

**It resolved nothing wrongly**, which is why it was invisible and why it was
not an exposure. Measured on both installed instances before the fix: the
lockfile digest on disk, inside each image, and inside each running container
were one value, that value was the released source's, and Fastify resolved to
the same 5.12.5 in the lockfile and on disk everywhere. The fault was a
manifest disagreeing with its own release, which is the class of problem the
beta.63 timestamp work was about, so it gets a gate rather than a note: a test
now reads both places npm writes the version and names the command that fixes
a mismatch.

## Two reads of two people are two requests

`browser_tasks_active_key` allows one PENDING or RUNNING browser task per
account, because a Chrome profile is held by one process and two browsers on
one profile is a real conflict. That index was right and is unchanged.

What was wrong is what happened on collision. A second request superseded the
first, on the reasoning that pressing a button twice means "do it now" rather
than "do it twice". That is true for Connect and for a sign-in, where the
second press is the same intention. It is false for a read, where the second
request names somebody else: asking to read two people read only the second,
and the first ended `SUPERSEDED` with "Replaced by a newer request for the same
account". Measured on a real installation: two requests, one observation.

Requests that name a target now wait their turn. `QUEUED` sits outside that
unique index, so several may wait while exactly one runs, and exclusivity stays
the index's to enforce rather than the application's. The worker promotes a
waiting request only while its account has nothing active, oldest first, so a
read that has been waiting is served before one that arrived a moment ago. Two
requests for the same person coalesce into one. Twenty waiting is the bound, and
the twenty-first is refused with a sentence rather than dropped, which is the
whole fault being fixed. Sign-in requests keep replacing one another, because
there a newer request really does supersede an older one.

## The confidential canary, as one command

`npm run hosted:canary` renders the whole of the outstanding hosted proof: for
each provider, the exact credential it is missing and where that credential
comes from, the provision request verbatim with its monthly cost and the
security properties it asserts, the key release policy and what that policy
binds, and every operation needing a live provider shown as the call it would
make. Then what a canary would prove, what it would **not** prove, and the eight
steps in order. `-- --emit <dir>` writes each body to a file beside the one
command that sends it.

It exits non-zero while it is blocked, so it cannot be mistaken in a script for
a canary that passed. Nothing in it provisions, pays for or contacts anything.

## Also

- The Phase 1 barrier item about installed instances reads each one's own
  `BUILD_INFO.json` instead of carrying a hardcoded verdict. A verdict that
  cannot be wrong cannot be right either.
- Four tests waited a fixed interval for a side effect they could not await,
  which passes on a developer's machine and fails on a loaded CI runner while
  reporting itself as a product bug. They wait for the signal now.
- Two structural tests joined paths with `node:path` and compared them against
  forward slashes, so three cases passed on Linux and failed on Windows.
