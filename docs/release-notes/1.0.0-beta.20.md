**The browser now opens on macOS.** Creating an agent on a Mac and pressing Connect produced no Chrome window and nothing on screen to say why. That is fixed, along with eight other faults found in the same sitting.

**If you are on a Mac, this is the release to be on.** Nine separate things were wrong, and one of them meant the product's central feature could not be used at all.

---

## Connecting an account did nothing

The worker was told to open Chrome at `/app/storage/browser-profiles/<account>` — a path that exists inside the API's container and nowhere on your Mac. Chrome is given its own profile directory to create, so it tried to create `/app` at the root of a read-only volume, and every attempt died in about half a second:

```
ENOENT: no such file or directory, mkdir '/app'
```

The account went to `offline` with that as its detail. What you saw was a button that did nothing, because the one screen that would have told you — `ai17z doctor` — was counting accounts rather than reading their health, and said "1 connected" and "Nothing is broken". That is the seventh fault below, and this is what it was hiding.

`resolveProfileDir` was written to prevent exactly this. Its own documentation said the stored path is not trusted across machines and the local one is derived from the account id. The function ignored its argument and returned the derived path — correct — but **nothing on the macOS path called it.** The runtime read the stored value straight out of the database row, and the API wrote a container path into that row at account creation.

So there was a guard, a comment explaining why the guard mattered, and a test file named after it, while the code that needed it went around it. Three things now hold it shut:

- The API writes **no path at all**. It runs in a container whose working directory is `/app`; it cannot know where your browser profiles live, and a guess recorded as fact is worse than an absence.
- The runtime resolves the path through `resolveProfileDir`, every time.
- A unit test asserts that `/app/storage/browser-profiles/abc-123` is never the answer, on any platform. It is a unit test on purpose — the integration test that drives real Chrome skips on any machine without Chrome, which is every machine that builds these packages.

This was reported from Windows in a different form and fixed there. The Mac had never exercised it.

## The `ai17z` command did not work at all

`~/.local/bin/ai17z` is a symlink into the installation. The launcher worked out where it lived using the directory of the path it was invoked as — which, through a symlink, is `~/.local/bin`. It then looked for the application there, found nothing, and failed. Every command: `start`, `stop`, `doctor`, `update`.

It now resolves the link chain, including relative links, before deciding where it is.

**This matters for updating.** On Beta 1.0.0 (19) the `ai17z` command is broken, so the updater must be run by its real path:

```
"$HOME/Library/Application Support/AI17Z/AI17Z/ai17z" update
```

After this update the `ai17z` command works normally again — the updater replaces the launcher itself, and the symlink already points at it.

## The version screen told Mac owners to run a PowerShell script

The update panel has instructions per installation method, and the method is worked out inside the API from a marker the launcher passes to the containers. Both Unix launchers passed it correctly. The function reading it only knew two of the five values — the two that existed before macOS and Ubuntu did — so it discarded `MACOS_PKG`, fell through to its last resort, and that last resort is a check for a file (`BUILD_INFO.json`) that is not among the files the container image is built from. It can therefore only ever answer "a developer's checkout" there.

Windows was unaffected only because `INSTALLER` happened to be one of the two values named.

So an unrecognised marker produced a confident wrong answer rather than an unknown one. The method list now has one home in `@xbam/shared` and is read off it, so a platform added there cannot go missing here; the panel carries instructions for all five; and a Mac is told `ai17z update`.

## Updating did not replace what was running

`docker compose up -d` builds an image only when one is **missing**, never when it is out of date. So an update on macOS or Ubuntu replaced the files on disk and went on running the containers built for the version before it. The health screen reported the source as unknown, because nothing had ever labelled those images.

Windows has compared the label against the installed build since Beta 1.0.0 (8). Both Unix launchers now do the same: each image carries the version and build time it was made from, and anything that disagrees is rebuilt before the stack starts.

**So the first start after taking this update rebuilds the containers, and that takes several minutes.** It says `Rebuilding the containers for this version` while it does. This happens once: every image on an installation older than this one is unlabelled, so all three are replaced. Starts after that are as quick as before.

## The 1.0.0 upgrade would have been refused

Both Unix updaters asked the shell whether a release was newer — `sort -V` on macOS, `dpkg --compare-versions` on Ubuntu. Both rank `1.0.0` **below** `1.0.0-beta.19`, because neither implements semantic versioning's rule that a release outranks its own prereleases. Checked against both commands rather than reasoned about.

The report that found this flagged macOS. Ubuntu had the same fault by a different route and was not mentioned; it was found by running the pair through `dpkg` rather than trusting the report's scope.

The consequence, plainly: **an installation that stayed on a beta would have refused the finished 1.0.0 as "not newer" and had no way forward but a reinstall.** Both now ask the application, through the same bridge the compatibility gate already uses, and `compareVersions` in `@xbam/shared` is the single implementation. A test runs the bridge on that exact pair.

Beta 1.0.0 (20) is reachable from (19) — the old comparators both accept it, which was checked. This is the last release at which that stops being true.

## A restart accused you of closing your own sign-in window

An account waiting for sign-in, the Chrome window open on screen, `ai17z restart` — and nine milliseconds after the stop signal the account was marked "the sign-in window was closed before it finished". Nobody had closed anything. Shutdown detached from the browser underneath a check that was midway through reading the page; the check correctly saw an unreachable browser, and wrote that down as your doing. The account still said it needed signing in after the restart finished, so the damage outlasted its cause.

Stopping now waits for a check in flight instead of racing it, refuses to start new ones, and a browser that goes away during shutdown changes no account's status. Somebody genuinely closing the window still does, which is the half that has to keep working.

## The diagnostics said everything was fine

`ai17z doctor` counted account rows and called every one of them connected. On a Mac whose only account was offline with every sign-in failing, it reported "1 connected" and finished with "Nothing is broken."

It now reports accounts by health, quotes the first failure, and has a row for the browser as the API sees it — the one question somebody has when a browser will not open, and the one thing it never mentioned. It also no longer creates the directory it was probing, having said at the top that it changes nothing.

## Smaller things

- **The browser log was erased on every start.** Starting again is exactly what somebody does after a failure, so the reason for it was gone before anyone looked. It is appended to now, rotated at 5 MB, with a marker for each start.
- **Setup said Chrome was missing on every Mac that had it.** It only knew where Linux keeps Chrome. A warning that is wrong is worse than none — the next true one reads as noise.
- **A packaged copy was told to run `./start-ai17z.sh`**, a script for a clone. It is told `ai17z start`.

## What holds these shut

Every fix has a test that was checked by putting the fault back and confirming the test caught it. Twenty-six of them, one at a time: a test written after a fix passes by construction, and that proves nothing about whether it would have noticed.

Four were not load-bearing on the first attempt and were rewritten rather than accepted. One passed against a renamed function when it was only checking the name; one was satisfied by a per-user Chrome path after the system-wide one had gone; and two shutdown guards were each masked by a different guard that happened to fire first, so the test could not have told which one was doing the work.

The first version of the version-comparison fix put a byte-identical function in each of the two updaters. That is the shape of the fault it was fixing — each platform with its own copy of one rule, both wrong the same way — so it was replaced with one implementation in the file both already load.

## Everything else

Unchanged from Beta 1.0.0 (19): Windows, macOS on Apple Silicon and Intel, Ubuntu 22.04 / 24.04 / 26.04 on amd64 and arm64, each package built on a machine that really is that architecture. Installation commands, paths, data locations and security posture are all the same. The macOS packages remain unsigned and not notarized, and nothing here disables Gatekeeper or strips a quarantine attribute — `docs/MACOS_TRUST.md` is the long version.
