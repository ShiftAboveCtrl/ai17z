**One mistake, found in three places, all of them about which program is holding the browser.** AI17Z has always said that only the worker owns browsers. What was missing everywhere is that a process has to know whether it is that worker.

## A capability the model was offered and could never have run

Asked what an account had been posting, the agent shortlisted a read of X, was offered it as one of eight, chose it, and then failed inside the implementation with "Google Chrome could not be found".

Every gate said yes. Readiness was the one that should have said no, and it was asking the wrong question: whether *any* browser worker is running anywhere in this installation. One was. It simply was not the process that had taken the job. A worker running without a browser passed that check every time, and then met a Chrome that is not there and is never going to be.

Readiness answers about the program asking it now, as well as about the installation. An unset role still means fully capable, which is what a checkout, a single-process installation and the test suite all are, so nothing that could drive a browser loses the ability to say so.

## Half an agent's own engagement, lost to a coin toss

The same shape, one layer out. The loop that turns a decision to like or repost something into the act was started by every worker, whether or not it could act. Measured on a live installation inside a single minute, on one account: three of those failed permanently with the same missing-Chrome message while two succeeded, the failures from the worker without a browser and the successes from the one with it.

The noise in the record was the smaller half. The claim that selects a proposal also moves its attempt forward, so a worker that cannot act spends the attempts a proposal is given, and something the capable worker was about to do is given up on instead. Started only where a browser can actually be driven now, which is the same gate the tab reporter beside it already used.

## A session that had lapsed, noticed where it would be noticed first

Beta 4.5 made a read that finds X asking for a sign-in record it, so an installation in that state stops reporting itself as healthy. That covered a read somebody asked for.

The radar polls on its own schedule against every source an owner has added, so it meets a lapsed session long before anybody opens a screen. That path had its own handling and only wrote a sentence onto the source's row. Both paths record it now, under the same rule: only for an account that was connected, and never for a rate limit, because sending somebody to re-authenticate a working account over a slow-down is worse than saying nothing.

## A correction to what Beta 4.5 said

Beta 4.5 described the posting jam as lasting twelve days. That was two facts run together, and the runtime says otherwise.

The blocked idea and its job were twelve days old, created on the 7th. Posting itself was working until the 17th: the last post went out at 02:31 that morning. The jam began at 07:21 the same day, when the job was rejected and the idea returned to the backlog to win every selection from then on. The outage was about two and a half days, not twelve. A newer idea created that evening was never reached.

The fix is unchanged. The description of how long it had been happening was wrong, and the comment in the code now keeps the two dates apart.
