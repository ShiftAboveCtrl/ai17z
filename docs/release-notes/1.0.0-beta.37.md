**Eight things AI17Z got wrong about itself, and two answers to questions that already had one.** Four are sentences an owner reads that state more than was known. One is a check whose own report came back empty. One is a screen that showed nothing waiting while something waited. One let the same post go out twice. The last wrote a live account's session off on the strength of having looked in the wrong place.

They were found by running the installations and reading every screen against what the database and the audit log actually said, which is the only way this kind of fault surfaces. Nothing was failing. Each one is a confident answer, and a confident wrong answer looks exactly like a confident right one.

## An account marked signed out by something that was never signed in

The worst of them, and the one that had already happened.

When a read of X comes back asking for a sign-in, that is recorded against the account so an installation in that state stops reporting itself as healthy. Beta 4.5 added it and Beta 4.6 kept it. What neither asked is which program is doing the reading.

A sign-in demand means the profile that was read has no session in it. That is a fact about the account only when the profile read is the one the account's session lives in, and the profile directory is derived locally from the account and wherever the program asking happens to keep its storage. That derivation is deliberate: a stored path is not trusted across machines. It also means a program running from somewhere else derives a different directory, finds an empty profile, is asked to sign in, and knows nothing whatever about the installation.

Measured: a process run outside an installation opened a browser on a profile that had never been signed in, and a healthy connected account was marked as expired while the real signed-in browser beside it was serving four tabs.

The check that existed asks whether the installation has a browser worker. It was true throughout, which is exactly why it did not help. The question had to be whether the caller is one, and the answer is the worker registration, because the worker is the only thing that writes one. A script, a harness, or a checkout has no row and is now ignored.

The same rule was written out twice, once in the read path and once in the radar's own handling, so the guard would have had to be added to both or protect neither. There is one of them now.

## Four working models reported dead

An agent's chosen model is checked against the list its provider gave. Absent from the list, the screen said the provider no longer offers it and the agent cannot generate with it, in red.

Both halves are conclusions. The only fact underneath is that a name is missing from something stored earlier.

Measured on a live installation: that sentence was shown against four of the seven roles at once. The stored list was five days old and had never been refreshed, and the model it said was gone had completed twelve calls in the previous three hours. An owner reading that screen would have gone and reconfigured four roles that worked.

The neighbouring case already had the right instinct, since an empty list is explicitly not treated as evidence a model is missing. A list that is merely old is the same kind of not-evidence. The row now says what was noticed and when the list was taken, and leaves the conclusion where it belongs. The warning stays, because an agent pointed at a genuinely retired model does read as healthy everywhere and fail every generation.

## A tool reported switched off while it was answering

The built-in tools and the Toolspace capabilities are separate on purpose and documented as such. What that did not account for is that the three built-in tools have capabilities covering the same ground, with the same names, because the purposes are the same.

So the health screen said "Current time is switched off for this agent" and "Own status is switched off for this agent", while the capability audit for that agent in that hour recorded the clock answered and the diagnostics answered. The same words, from two subsystems, making opposite claims, on the one screen whose purpose is answering whether it is working.

The split is not changed. Each row now says which of the two it is talking about.

## A refusal that named a cause it had not established

Asked how a post did, the reader navigates to the figures and refuses when there are none. The refusal said only the author's own posts have them.

That is one of three possible causes stated as the finding. The code's own comment already said it could not tell them apart. Measured against two posts the signed-in account had written itself: both refused with that sentence, the agent repeated it to its owner, and then went further and explained a mechanism that does not exist.

It now says no figures were shown and names what that can mean. The third possibility, that the page it asks for is no longer where the figures are, is written down as the open question rather than guessed at, because this is the only place in the reading layer that builds that form of address.

## A subject attributed to an account with no name

The subjects several accounts have started using are counted by identity, preferring the numeric id, because a handle changes and the same person then counts twice. The examples beside them were drawn from the same set and written as names.

So an account whose id was known was rendered as its id, and a post carrying neither an id nor a handle became an empty string that was rendered as a bare "@" and counted as one of the accounts. Seen as "326 accounts, including @\_anika\_7, @, @nathanoyler".

Counting and naming are different questions. They have separate answers now, and an author nobody could identify is not an account, for the same reason an unmeasured count is never zero.

## A retry that could never once have fired

Two releases in a row failed the same qualification job, and the second showed why the guard against it did not work.

The job retries when the published installer is refused, because it runs the command a stranger runs and that asks GitHub without a token, against an hourly ceiling shared with whoever else is on the runner. The retry was conditional on finding a rate-limit code in the output.

The installer says everything through the host stream, and only the error stream was being captured, so the output was empty on every run the job has ever done. An empty string matches no code. Beta 4.6 failed with "exited 1:" and nothing after the colon, and no retry ran.

A retry has to turn on the thing that failed, which is the attempt. Every stream is captured now, the retry turns on the exit status, and both the Mac and Ubuntu installers were changed the same way for the same reason. It is still exactly two attempts, still ninety seconds apart, and a second failure is still a failure. What is new is that the report says which kind it was, because a shared runner's bad hour and a broken installer need opposite responses.

## A decision nobody could reach, for the second time

"What needs you" is the first screen an owner opens, and it said nothing was waiting while a job sat held for a decision eight days old.

This has happened before and was fixed before, and the principle it was fixed on is the one that fixes it again: something waiting on a decision must be reachable, or the decision cannot be made. Last time the list was driven by inbound message types and the waiting work had arrived on a scheduled trigger, so it was counted by the badge and shown by nothing.

This time the list was complete and the window was not. It is capped, the cap is applied after ordering by arrival, and a busy account fills it: outreach showed exactly two hundred, which is the whole cap, and the thing needing a decision was behind all of it.

The counts are deliberately taken from the rows the list returns, so the chips cannot disagree with what is under them. That makes the ordering the only place to correct it without giving that up. Anything waiting on a person now sorts ahead of the window, so the cap trims outreach, which is what a cap is for, rather than trimming the one bucket the screen exists to show.

## The same post, twice, two points under the line

A live account published two original posts four days apart with a byte-identical opening sentence, a byte-identical closing sentence, and one clause changed in the middle. Nothing stopped it and nothing said so.

The guard saw it. It scored the pair at 78, named the match, and recorded both in the quality trace. The rewrite threshold is 80, so nothing was asked for, no repetition event was raised, and the line an owner actually reads said the draft sounded like the agent. Finding out why it had said nearly the same thing twice meant knowing to open the data of a different event.

Two things were wrong. The score is decided by the strongest single signal, and the branch that recognises an identical opening sits behind the phrasing overlap it was competing with, so a pair sharing a whole opening sentence was judged on its percentage. And a post is not a reply: a reply opening the same way to two different people is mildly repetitive and nobody sees both, while a post opening the same way twice goes to one timeline where the two sit above each other.

An identical opening is now decided first on an original post, and scores above the rewrite threshold on its own. Replies are unchanged, and the same pair still scores 78 as a reply. The rule is about the opening rather than the subject, so an agent may still return to something it cares about.

Anything that matched is written down now whether or not it crossed the line, with the score, the threshold and which side of it this was. Something noticed and not acted on is worth more in the record than in nobody's.

## Two routes answering questions that already had answers

Both were registered, implemented, and called by nothing.

One returned who leads somewhere an agent does not already reach. The People screen returns the same call with the relationship and whatever has been read about the person attached, so this was the same query with less in the answer.

The other returned every capability flat, while the packs view returns the same set grouped. That one had already cost something: it was what an individual switch reloaded, while every row on screen came from the pack view, so changing a capability refreshed nothing anybody could see.

Removed rather than given surfaces of their own. Two answers to one question is the thing this codebase keeps saying it does not want, and the one nothing renders is the one that goes quietly wrong.

The two that looked the same and are not are the playground and the Response Lab. The Lab runs the real pipeline as a rehearsal; the playground holds memory, thread and research still so two personas can be compared with everything else fixed. Neither answers the other's question, the playground has no screen on purpose, and it now has tests covering the part that had none.
