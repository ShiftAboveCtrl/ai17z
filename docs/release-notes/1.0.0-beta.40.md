**A decision an owner could not reach, fixed twice.** The first fix was correct about the cause and wrong about the SQL, it had a test that proved it worked, and it did not work. Only the installed product showed that, which is the part worth writing down.

## What was wrong

"What needs you" is the first screen an owner opens. It is a list capped at two hundred rows and ordered by arrival, so on a busy account the cap fills with things nobody has to decide anything about and a job genuinely held for a person falls off the end. Measured: the screen said nothing was waiting while a job eight days old sat in review.

The correction was to sort anything waiting on a person ahead of the window, so the cap trims outreach rather than decisions. That is still the right correction. It was written as an ordinary comparison on the job's status, and most rows in an inbox have no job at all: something was recorded and nothing was queued for it, which is what a keyword match usually amounts to. The status on those rows is null, a null comparison is null rather than false, and a descending sort puts nulls first. So every row nothing was queued for sorted ahead of the decision the change existed to rescue, and the screen went on saying nothing was waiting.

It is a coalesce. That is the whole fix, and it is the kind of thing that reads as noise in a diff.

## Why the test did not catch it

The test built a window's worth of noise and checked that a held job survived it. Every noise row it built carried a job, because that was the convenient thing to write, and no row it built had a null status. The defect lived entirely in the null case.

So a passing regression test reported that a fix worked when it did not, for two releases. What caught it was running the installed product against a number written down in advance: the count of decisions waiting said one, the screen said none, and those two cannot both be right.

The test now builds noise in the shape a real inbox has, half with jobs and half without, and checks the rows without jobs are genuinely in the answer before testing how they sort. It fails without the coalesce.

## What this is worth

Nothing else in this release. It is one word of SQL and a test that now tests the thing it claimed to.

The general lesson is cheaper to write down than to learn again: a fixture built out of whatever was convenient tests the case that was convenient. When a fix is about ordering, or nulls, or absence, the fixture has to contain the absence.
