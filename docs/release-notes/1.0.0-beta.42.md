**An agent watching a repository could stop its owner from updating.** Both things ask GitHub, both were spending the same sixty requests an hour, and the one that lost was the updater. It refused correctly rather than guessing, which is the only reason this was a nuisance instead of a bad install.

## What happened

An unauthenticated address gets sixty GitHub API requests an hour. That allowance is per address, not per program, so everything behind one connection shares it.

An owner who points an agent at a repository to watch gets exactly what they asked for: it polls that repository through the API, several endpoints at a time, on a schedule. Two installations on one home connection during an active week will spend sixty an hour between them without either doing anything wrong.

What then breaks is not the watching. It is the update check, which asks the same API which release is newest. Measured on a real machine: the budget read `0 of 60`, the newest release was published and downloadable the whole time, and the updater reported that it could not reach GitHub to see which version. It changed nothing, which is the right answer to not knowing, and it also meant the update could not proceed.

Waiting does not fix it, because the agents are still running and spend the next hour's allowance too.

## Where an update looks now

Two addresses, neither of which is the API.

The releases feed is ordinary `github.com`, is not charged against that allowance, and lists prereleases. That last part matters here: `/releases/latest` was never usable for AI17Z because it hides exactly the releases this product ships, and the feed does not. Measured across three consecutive fetches, the API budget read 56 before and 56 after.

Once the feed has named a release, every file of it is fetched at its own tag. Nothing is looked up, because nothing needs to be: the names are fixed by the release and there is already one place in this repository that spells them.

So an owner updating and an agent watching no longer draw on one budget, and neither can starve the other. Nothing here needs a token, and there is nowhere for one to be sent.

## What it refuses to do

A release appears in the feed the moment it is created, and its packages arrive afterwards. So the feed naming a release is not taken as the release being installable: its manifest has to be there too, and the version that manifest states has to be the version its tag claims. A release that is half published, or whose manifest disagrees with its own tag, is refused by name rather than offered.

A check that fails still resolves to nothing at all. That was already true and is worth keeping true, because the next thing that happens after a check is an install.

The bytes are checked exactly as before. Where an update finds out what exists has changed; what it verifies before installing it has not.

## The watcher was already well behaved

Worth saying, because the obvious fix would have been to make the agent ask less, and that would have been the wrong repair. It already sends a conditional request whose unchanged answer GitHub does not charge for, already backs off when it fails, already stops when told to slow down, and is already capped at an hour between polls. None of that was the problem. Two correct programs sharing one small budget was.

## The scenario harness could not be run where it matters, and said nothing was wrong

Found while running it against a real installation to check the above, which is the only way any of this would have surfaced.

It worked out where the signed-in browser was by building a path by hand: relative, and without the segment that keeps two installations on one machine apart. So it resolved against whatever directory it was started from. Against a real installation it found nothing, and against a stale file left in a checkout it connected to a port whose browser had been gone for days. Three copies of the same line, in one file. It asks the one function that answers this now, like everything else does.

Then, pointed at an agent whose automation is set to manual, every one of its scenarios was recorded and none was queued, and it printed `0 scenarios, 0 problems` and exited successfully. A harness that tested nothing must not read as a harness that found nothing wrong. Scenarios that never ran are now counted, named with the reason, and fail the run. The one scenario where queueing nothing is the pass stays the pass.

It also names the agent it is driving, which is what lets it run at all on an installation set to manual. That changes nothing about what it may do: an agent switched off still does no work, every job is still asserted to be a rehearsal, and publishing still needs an explicit count on the command line.
