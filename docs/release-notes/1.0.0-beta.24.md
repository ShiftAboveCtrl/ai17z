**Your agent's mention monitors could stop for an hour and the screen would say everything was fine.** This release is why that happened, measured rather than guessed, and what now stops it.

---

## Three monitors dead, one perfectly healthy

The report that started this:

```
Mention search          21 failed poll(s) in a row    Last worked 51m ago
Notifications           Polling normally
Replies to own posts     7 failed poll(s) in a row    Last worked 46m ago
Reply search            23 failed poll(s) in a row    Last worked 52m ago
```

and Chrome showing **Aw, Snap! Out of Memory** on an X tab at the same time.

That asymmetry is the whole diagnosis. Mention search, reply search and replies to own posts **all share one browser tab**. Notifications has its own. One tab had stopped, and everything that needed it had stopped with it.

## What was actually happening

**X's own application had filled the tab.** Measured on the running browser: the mentions tab was holding **3,754 MB of the 4,192 MB** a Chrome tab is allowed, with only 1,546 elements on the page. So it was not the page being large. Forcing a collection freed **24 MB of 3,801 MB**, so it was not memory waiting to be tidied either. It was genuinely held, all of it inside X's own code, and none of it is AI17Z's to release.

Growth was about **100 MB per search**, which fills a fresh tab in well under an hour.

**Then the tab was never given back.** An operation picked the tab up, the tab ran out of memory underneath it, and what it was waiting for never came back. Nothing existed to take the tab away from it. Every later read waited two minutes and gave up, over and over, while the panel reported the tab as **busy** — a word that sounds like work is happening.

AI17Z had a limit on how long something may **wait** for a tab. It had none on how long something may **hold** one.

## What changes

**A tab can be taken back.** If one operation holds a tab too long, AI17Z takes it back, says so, and the next read works. One poll fails instead of an afternoon of them.

**A tab that is being held too long now reports as failing**, not as busy, so it shows up as something wrong rather than as something in progress.

**AI17Z asks a tab whether it is alive rather than looking at it.** A tab killed for memory keeps its address bar exactly as it was — the dead one still read `x.com/notifications/mentions` an hour later — so nothing about how it looks gives it away. Now it has to answer, within five seconds, before it is used again.

**Tabs get replaced before they die.** AI17Z watches how much memory each X tab is holding and replaces it while it still can, rather than waiting for Chrome to kill it. Replacing a tab opens a fresh one **in the same signed-in browser**: your X session, your profile and your cookies are untouched.

**And you can see it happen.** The browser panel now says:

> Replaced 2 minutes ago: it was holding 2,530 MB, 60% of what this renderer is allowed.

Recovery you cannot see is indistinguishable from a fault. Without that line, a tab running out of memory and being replaced *correctly* looks exactly like a run of failed polls that nobody fixed.

## AI17Z now works out what your machine can spare

The wrong fix for all of this is to ask for more RAM. AI17Z runs on your own computer, beside your editor and your own browser, and a local-first product that needs the machine to itself is not local-first.

So AI17Z works out what it may use from what you actually have. On a smaller machine it keeps fewer X tabs live, runs less at once, and replaces tabs sooner. On a large one it has more room but still leaves plenty: **Chrome never gets more than half the machine**, at any size.

When memory gets tight, background work **waits** rather than being dropped, and the health screen says so in words:

> Memory is tight, so AI17Z is running less in the background.

A machine that will not report its free memory is treated as ordinary rather than as small. Doing less on hardware that was fine is its own kind of bug.

## Your agent stops using dashes as pauses

An em dash is the single most reliable sign that a machine wrote something, and AI17Z has had a rule against them for weeks. Four of the replies ai17zos has actually published carry one anyway, all written after the rule existed.

The reason turned out to be the order things happen in. The check ran, stripped the dashes, and then the step that rewrites a draft to sound more like your agent ran **afterwards** and put them back, working from instructions that had never mentioned punctuation.

Now the rewrite is told the rule, and its output is checked as well. Written correctly in the first place reads better than repaired, so both.

**The rule also covers what a keyboard can type.** A model told only about em dashes reaches for `--` or a spaced hyphen instead, and those read exactly as machine-written too.

**Hyphens inside words are untouched, and there are tests for each of them:** `read-only`, `owner-configured`, `v1.0.0-beta.24`, `--dry-run`, `3-4pm`, and every URL. A rhetorical dash has spaces on both sides; a hyphen inside a word never does. Even `npm run verify:install -- --twice` survives, because that is a command somebody pasted rather than a sentence.

## One more thing, from the last release

Both of the routes that install AI17Z write an entry in Add/Remove Programs, and they used different names for it — so a copy installed one way and updated the other way ended up with two entries for one folder, the older one frozen at whatever version it was installed with. Uninstalling through the stale one would have removed the current installation while telling you it was removing something from months ago. Updating now retires the entry it replaces.
